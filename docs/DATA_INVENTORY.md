# Routely Data Inventory

Version: `2026-10-27.1`  
Last audited: 2026-10-27

This inventory reflects the application code and deployment information currently present in this repository. It is an engineering record, not legal advice. Provider retention settings and the operator's legal identity/contact details still require confirmation.

## Data Collected and Stored

|---|---|---|---|---|

## Third Parties

- **MongoDB Atlas:** stores user, route, trip, ticket, payment-attempt, and operational records described above. Region, backups, access controls, and provider retention must be confirmed by the owner.
- **Render:** hosts the frontend/API and processes API requests and operational logs. Hosting region, access, and log retention must be confirmed.
- **Resend:** delivers account and trip emails. Receives recipient addresses and the specific email content described above; its processing/retention terms must be confirmed.
- **Paystack:** hosts checkout, processes payment and refund requests, receives the customer's email, amount/currency, reference, callback URL, and booking/ticket identifiers. Card details are handled on Paystack's hosted page and never touch Routely servers. Paystack retention and applicable transfer terms must be confirmed.
- **OpenRouteService:** may receive origin and destination coordinates to calculate road distance. Route coordinates only are sent; no personal data is intentionally included. If no API key is configured, the application calculates straight-line distance locally.

## Tracking and Analytics

The current frontend source contains no analytics, advertising, tracking pixel, or behavioral tracking integration. The admin dashboard's booking/revenue reports are operational database reports, not a third-party analytics tracker. There is no intentional tracking-cookie feature. The application stores authentication state in `localStorage` as described above. Do not add analytics, advertising, pixels, or tracking SDKs without first updating this inventory, the Privacy Policy, and `LEGAL_VERSION` in the same commit.

## Retention and Deletion Limits

The application currently has no scheduled purge for user accounts, tickets, payment attempts, email-provider records, or application logs. A one-day JWT expiry and 15-minute reset-link expiry are not equivalent to a data deletion schedule. Account deletion expires outstanding pending reservations (releasing their seats), cancels/refunds upcoming paid tickets before anonymisation, removes direct account identifiers, credentials, reset/terms fields, and checkout authorization URLs, and keeps ticket/payment records linked to a pseudonymous account identifier for accounting/refund follow-up. Account deletion requests cancel upcoming paid tickets independently of the ordinary passenger cancellation cutoff; refund amount follows the configured full-ticket-amount refund function. **The owner must confirm the required accounting retention period and provider-side retention/backup deletion settings before launch.**
